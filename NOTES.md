# Zerodrift NOTES

## Architecture

## Money rules
Enforced twice, in code AND in the database (ledger migration `0001_ledger_schema.ts`):
- **Integer minor units**: `bigint` in TypeScript, `BIGINT` in Postgres; amounts travel as decimal strings in JSON. `@zerodrift/db` parses BIGINT to `bigint`. Fees use integer math, **round half up** (`feeFor`); a partial refund returns the fee share rounded **down** (`proportionalFee`).
- **Immutable journal**: trigger rejects UPDATE/DELETE/TRUNCATE on `journal_entries`; corrections are reversing transactions.
- **Debits == credits**: validated in code before writing AND by a **DEFERRABLE INITIALLY DEFERRED constraint trigger** at COMMIT. Deferred because entries are inserted one at a time (balanced only once all are in); the DB then refuses to commit an unbalanced transaction from any code path or manual SQL.
- **No negative balance** unless `allow_negative`: code check with a clear error, plus a BEFORE trigger on `account_balances` as the backstop.
- **Currency**: composite FK `(account_id, currency) -> accounts(id, currency)`, so an entry can never use a currency different from its account.
- **Concurrency**: `SELECT ... FOR UPDATE` on balance rows, always acquired in ascending account id order (`ORDER BY account_id FOR UPDATE`); holds lock the hold row first, then balances. A deadlock needs a lock cycle, a global order makes cycles impossible. `inTransaction` still retries 40P01/40001 as cheap insurance.
- **Idempotency**: `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` claims the key inside the posting transaction. A concurrent duplicate **blocks on the unique index** until the first commits (then returns its stored response) or rolls back (then it runs). Same key + different request hash => 422 `idempotency_key_reuse`.
- **Timeouts are UNKNOWN outcomes** (payments-service, Phase 3).

## Decisions and tradeoffs

- **GitHub remote (overrides brief "never push")**: on 2026-10-28 the user explicitly asked to push everything to their GitHub repo and keep it updated. Rule from now: push after every phase commit (and big milestones) once the remote exists. Remote URL and auth are supplied by the user; tokens are never pasted into chat or committed.
- **Kafka client: @confluentinc/kafka-javascript** (v1.11.0, last release 2026-10-07). KafkaJS 2.2.4 was last published 2023-02-27, so it is effectively unmaintained.
- **Circuit breaker: opossum** v10.0.0 (published 2026-08-03).
- **DB layer: Kysely** (v0.29.7, active as of 2026-10-17); chosen over Drizzle for explicit SQL control (`FOR UPDATE`, isolation levels) in the ledger.
- Other verified versions: NestJS 12.3.2, zod 4.6.7, pino 10.4.0, vitest 5.0.5, prom-client 15.1.3.
- **TypeScript 6.0.x, not 7**: `pnpm add typescript` resolves to 7.0 (native port), but typescript-eslint 8.72 refuses to run on it ("does not support TS 7.0"). Pinned `typescript@6`. TS 6/7 no longer auto-load `@types/*`, so `tsconfig.base.json` sets `"types": ["node"]`.
- **CommonJS output, not ESM**: NestJS decorators + `emitDecoratorMetadata` are simplest on CJS. Vitest uses `unplugin-swc` because esbuild does not emit decorator metadata.
- **Shared packages are consumed from `dist/`** (`main` -> `dist/index.js`), so run `pnpm build` before `typecheck`/`test` (CI does this; `pnpm -r build` is topological).
- **Kysely 0.29 moved the migrator** to the `kysely/migration` entry point.
- **pnpm 12 blocks dependency build scripts by default**; `pnpm-workspace.yaml` `allowBuilds` allows only `@swc/core` and `esbuild`. With `CI=true` pnpm installs are frozen: use `--no-frozen-lockfile` when adding deps.
- **Host ports**: the user's other projects occupy 5432/5433/6379/6380, so Zerodrift publishes Postgres on **55432** and Redis on **56379**. Inside the Compose network services still use the standard ports.
- **Postgres image**: `postgres:17-bookworm` (the `postgres:17` image on this machine was corrupted by an interrupted pull).
- **Environment**: the network is flaky (DNS timeouts, TLS errors during image/npm downloads). Installs and pulls are wrapped in retry loops.
- **Database per service** in one Postgres instance (`ledger`, `payments`, `webhook`, `reconciliation`), created by `infra/postgres/init.sh`. No cross-database access. A shared instance keeps the local stack light; production could split them.
- **Config**: `@zerodrift/config` holds `PRODUCT_NAME`, topic names, and a zod-validated `loadConfig` that fails fast on bad env.

- **Ledger balance convention** (Phase 2): every account's balance = credits - debits, so a funded wallet is positive and `gateway_clearing` (the outside world) goes negative on top-ups. Hence **the sum of all balances is always exactly 0**: the strongest "no money created/destroyed" check, exposed at `GET /internal/invariants` (also verifies balanced transactions, balance == sum of entries, held == sum of active holds, no illegal negatives).
- **Holds**: create moves available -> held (no journal entry); capture posts a journal transaction that debits the payer *from held funds* and returns any unused remainder to available (so partial capture = capture + auto-release; one capture per hold); release/expire return funds. Expiry sweeper takes one hold per short transaction with `FOR UPDATE SKIP LOCKED`, safe with multiple replicas.
- **Reversal** posts the mirror image; `UNIQUE(reverses_transaction_id)` makes a double reversal impossible even concurrently; it refuses (409 `insufficient_funds`) when the money was already spent rather than going negative. Reversals cannot be reversed.
- **Refund design note**: partial refunds are modelled by payments-service as ordinary transfers merchant -> customer (fee share via `proportionalFee`); `reverse` handles full reversal of one ledger transaction.
- **Balances stored, not derived**: `account_balances` is updated in the same DB transaction as the entries (fast reads, row-lock target); the invariant checker proves it always equals the journal.
- **Testing choices**: one Testcontainers Postgres per test run (global setup, `TESTCONTAINERS_RYUK_DISABLED` since we stop it ourselves), a fresh database per test file. `TEST_PG_ADMIN_URI` reuses an existing server. Vitest configs are `.mts` to avoid Vite's CJS-config warning. The model-based property test (fast-check) funds wallets first and has a coverage guard so it cannot pass vacuously; invariants are global so a failure early in a run shrinks to a trivial sequence (known limitation).
- **Mutation check done by hand**: breaking the capture-remainder release made 4 example tests + the property test fail, so the tests do detect that bug class.

### Phase 3 decisions (payments-service + mock-gateway)
- **Flow**: customer funds are HELD in the ledger, the gateway (mock bank) is asked, then the hold is CAPTURED to the merchant (success) or RELEASED (failure). Wallet balance is the funding source; the gateway acts as the authorisation/risk step and produces the settlement file reconciliation uses.
- **Saga** (`saga.service.ts`): every step has a deterministic idempotency key derived from the payment id (`hold:<id>`, gateway reference = id, `capture:<id>`), progress is stored, so the saga can be resumed from any step by the request path, a gateway callback, or the recovery job. **A timeout / network error / 5xx / open circuit is UNKNOWN, never a failure**: the payment stays `processing`, funds stay held. Only a definitive answer (bank decline, ledger rejection) fails it, and a failed payment only becomes `failed` AFTER its hold has been released.
- **Lease** (`payments.lease_until`): short exclusive per-payment lease so the request path and recovery do not both work one payment. Not required for correctness (all steps idempotent, status moves are compare-and-set), it just avoids wasted calls. A crashed worker's lease expires.
- **Status changes** are compare-and-set (`UPDATE .. WHERE status = <seen>`) through `assertTransition` (state machine); losing a race returns the winner's state. Timeline row + outbox event are written in the same transaction.
- **Recovery job** (every 10s, also `POST /internal/recovery/run`): stuck payments (not leased, untouched for `RECOVERY_STUCK_AFTER_SECONDS`) are resumed in RECOVERY mode: ask the bank first (`GET /charges/:ref`). Known -> believe it. Unknown to the bank: young payment -> charge now (idempotent per reference); older than `RECOVERY_ABANDON_AFTER_SECONDS` -> `cancel` (writes a tombstone so a late/duplicate charge cannot succeed afterwards) + release hold + fail. If the bank succeeded but the hold has meanwhile expired, the bank charge is **voided** and the payment fails (customer never ends up charged without paying). It also finishes pending refunds, closes orphaned `in_progress` idempotency keys, deletes expired keys.
- **Gateway callbacks** only NUDGE the saga (which re-queries the bank itself), so duplicated, forged or reordered callbacks cannot change state. HMAC-signed, verified in constant time. Handled in the background with retries because they often arrive while the request still holds the lease.
- **Merchant idempotency** (`idempotency_keys`): claimed INSIDE the same DB transaction that creates the payment, so claim + resource commit atomically and a concurrent duplicate blocks on the unique index. Same key+request: stored response replayed (`Idempotent-Replayed: true`; a stored "202 processing" is answered with the CURRENT state instead of a stale snapshot); still running: 409 `request_in_progress`; different request: 422. Keys expire after 24h.
- **Circuit breaker**: opossum. Counts timeouts/5xx/network errors only (declines are normal results). Defaults: per-attempt timeout 1.5s, 1 retry with exponential backoff + full jitter (`@zerodrift/common` `retry`), opens at >=50% failures over >=10 calls in 10s, probes after 5s. Open circuit = instant UNKNOWN, no waiting. Exported metric `gateway_circuit_open`.
- **Refunds**: payment row locked, amount RESERVED, `pending` refund inserted (concurrent refunds serialise on the lock so they can never exceed the payment); one balanced ledger transaction (credit customer; debit merchant `amount - feeShare`; debit fees account `feeShare`); success -> payment `partially_refunded`/`refunded`; definitive ledger refusal (merchant already spent the money) -> refund `failed` and reservation released; timeout -> stays `pending` for recovery. Fee returned proportionally with cumulative rounding so all shares add up to exactly the fee.
- **API keys** are `zd_live_` + 256 random bits, stored only as SHA-256 (fast hash is fine for high-entropy keys, unlike passwords), shown once. Admin endpoints use a constant-time-compared token (`ADMIN_TOKEN`); dashboard JWT auth, rate limiting and audit log are Phase 8.
- **Top-ups** (`POST /v1/customers/:id/topups`) call the ledger directly (simulated bank funding, idempotent via the ledger key scoped by merchant). Not routed through the gateway.
- **Mock gateway** persists charges in its own Postgres DB (`gateway`, created on first boot via `ensureDatabase`) so killing/restarting it never loses what the "bank" did. Fault knobs (PUT `/admin/faults`): latency range, declineRate, errorRate (HTTP 500), lostResponseRate (processed but never answered), duplicateCallbackRate, callbackDropRate. A decline/success is decided ONCE per reference. Settlement file: `GET /settlement?date=YYYY-MM-DD[&format=csv]` (succeeded, non-voided charges).
- **Shared code moved to packages**: `DomainError` + `ErrorFilter` + `retry/backoffDelayMs` in `@zerodrift/common`, `makeEvent` in `@zerodrift/events`, `minorAmountSchema` in `@zerodrift/money`, `createTestDatabase` + Testcontainers global setup in `@zerodrift/testing` (ESM-only because it imports vitest).
- **Ledger gained** `POST /transactions` (generic balanced posting, used for the multi-source refund shape) and an `@zerodrift/ledger/app` entry point so integration tests start it in-process.
- **Outbox table + `emit()` exist now** (written transactionally with every state change); the Kafka publisher/consumers arrive in Phase 4.

### Bugs found by the Phase 3 tests (fixed)
- *Callback lost while the request held the lease*: the gateway callback arrived ~hundreds of ms after the charge, while the original request was still waiting out its timeout holding the lease; the handler found the lease busy, did nothing, and the nudge was consumed. Fix: acknowledge immediately and retry in the background until the payment settles. Test: "lost response but the async callback arrives".
- *Test isolation via the breaker*: `resetCircuit()` only closed the breaker but kept opossum's rolling failure stats, so later tests re-opened it immediately. (Realistic behaviour; tests now rebuild the breaker.) Property tests lesson: make the generators actually reach the interesting states and add coverage guards.
- *Flaky concurrency test*: asserting exact status codes under a 20-way burst in a single event loop was wrong; the right property is "one payment, one hold, one charge, customer charged once" (503/202/409 are all legitimate answers under load).

### Phase 4 decisions (outbox, Kafka, consumers)
- **Client**: `@confluentinc/kafka-javascript` through its KafkaJS-compatible API (`KafkaJS.Kafka`), librdkafka under the hood. Needs its install script (native binding download), allowed explicitly in `pnpm-workspace.yaml` `allowBuilds`. Producer is `acks=all` + idempotent producer.
- **New package `@zerodrift/kafka`**: `createKafka/createProducer/ensureTopics`, `emitEvent` (outbox write side), `OutboxPublisher`, `startOutboxRelay` (background connect + publish), `startIdempotentConsumer`, `createInboxTable`.
- **Topics** (`@zerodrift/config` `TOPIC_SPECS`): `zerodrift.payments.v1` (payment.*, refund.*), `zerodrift.ledger.v1` (transfer.completed), each with a `.dlq` twin. 6 partitions for the main topics (ceiling on consumer parallelism per group). Messages are keyed by aggregate id: one aggregate's events share a partition and stay ordered. Replication factor 1 (single local broker).
- **Outbox write** happens in the same DB transaction as the state change (`emit`), in payments (created/succeeded/failed/refund.created) and the ledger (`transfer.completed`, only when the posting is new, so a client retry emits nothing).
- **Outbox publish is AT-LEAST-ONCE by design**: one transaction takes a Postgres advisory lock, reads the oldest unpublished rows by `seq`, sends them (acks=all), marks them published, commits. A crash between send and commit re-sends the batch; that is expected and is exactly why consumers dedupe on `eventId`.
- **Why one publisher at a time (advisory lock)**: several replicas using `SKIP LOCKED` could publish two events of the same aggregate out of order. A single active publisher per outbox keeps order and fails over instantly (the lock dies with its transaction). Cost: one publish loop per service (fine here; shard by aggregate id if ever needed).
- **`seq bigserial` on the outbox** (migration 0002): `created_at` is the transaction START time, so two concurrent transactions can commit in the opposite order of their `created_at`; `seq` gives a stable read order. Per-aggregate ordering is still guaranteed because one aggregate's events come from sequential transactions.
- **Idempotent consumer**: handler runs in the SAME DB transaction as `INSERT INTO processed_events (consumer, event_id) ON CONFLICT DO NOTHING`; a redelivered event hits the PK and is skipped, so handler effects happen once although delivery is at-least-once. Offsets auto-commit only after the handler finishes (crash => redelivery, never loss). Transient failures retry in place with backoff + jitter (blocking the partition preserves per-aggregate order); after `maxAttempts` the message goes to the DLQ with headers (`dlq-reason`, `dlq-original-topic/partition/offset`, `dlq-attempts`, `dlq-consumer`) and the partition moves on. Invalid JSON / schema-invalid messages are dead-lettered immediately. If the DLQ publish itself fails the handler throws, the offset is not committed and the message is redelivered: nothing is ever silently dropped. Effects OUTSIDE the consumer's database (HTTP calls) are not covered by the inbox: handlers must write a job row and perform the call afterwards (webhook-service, Phase 5).
- **Why exactly-once delivery over a network is impossible** (for LEARN.md): the sender cannot distinguish "message lost" from "ack lost" (Two Generals), so it must either risk loss (at-most-once) or resend and risk duplicates (at-least-once). What we build is at-least-once delivery + idempotent processing (dedupe key + atomic effect) = effectively-once EFFECT.
- **Kafka down never blocks a service**: `startOutboxRelay` runs in the background and keeps retrying; services keep accepting writes into the outbox and the backlog drains in order afterwards. Verified live: services booted while Kafka was stopped, then published the backlog once it came up. `/ready` deliberately does NOT depend on Kafka.
- **Event schemas**: versioned envelope (`schemaVersion: 1`) in `@zerodrift/events`; adding an optional field is compatible, a breaking change needs a new versioned event type.
- **Test infra**: `@zerodrift/testing` starts real Postgres and a real single-node Kafka (`apache/kafka:3.9.0`, KRaft; `@testcontainers/kafka` only supports Confluent images, so a GenericContainer with the same listener layout as `docker-compose.yml` and a pre-chosen host port for the advertised EXTERNAL listener). Services' tests use `vitest.kafka.mts` when they need it.

### Phase 5 decisions (webhook-service)
- **Pipeline**: payments/ledger outbox -> Kafka -> `webhook-service` consumer (idempotent inbox) -> `webhook_deliveries` rows -> `DeliveryWorker` -> signed HTTP POST to the merchant. The consumer handler only PLANS deliveries (rows, in the inbox transaction). The HTTP call happens later in the worker, because an HTTP call cannot be rolled back with a DB transaction; doing it inside the handler would break the exactly-once effect the inbox gives.
- **One delivery row per (event, endpoint)**: `UNIQUE(event_id, endpoint_id)`, so Kafka redeliveries or publisher resends can never plan a second delivery. Verified by injecting the same event 3x into Kafka. Endpoints created after the event happened (1s clock-skew tolerance), inactive endpoints and non-matching `eventTypes` filters get nothing. Events without a `merchantId` (ledger transfers) are skipped.
- **Signature scheme** (`@zerodrift/webhooks`): `Zerodrift-Signature: t=<unix>,v1=<hex>` where `v1 = HMAC-SHA256(secret, "<t>.<rawBody>")`. The timestamp is inside the signed string so a captured request cannot be replayed later (receivers reject outside +/-5 min); constant-time compare; multiple `v1` allowed for rotation. Extra headers: `Zerodrift-Event-Id` (stable across retries: the receiver's dedupe key), `-Event-Type`, `-Delivery-Id`, `-Attempt`.
- **Secrets**: `whsec_` + 192 random bits, shown ONCE at creation/rotation, stored AES-256-GCM encrypted (we must read it back to sign, so it cannot be hashed; GCM detects tampering). Key from `WEBHOOK_ENCRYPTION_KEY` (32 bytes base64; the compose default is a DEV-ONLY key). **Rotation**: new secret signs together with the previous one for 24h so receivers can switch without downtime.
- **Retries**: attempt timeout 5s; success = any 2xx; redirects are NOT followed (could bounce to an internal address). Backoff = exponential with FULL jitter (`random(0..min(max, base*2^n))`, base 15s, max 1h) with a 1s floor so a retry is never near-instant; 8 attempts per cycle by default. After the last failed attempt the delivery becomes `dead` (the dead-letter state: stays in the log, stops retrying). Every HTTP attempt is stored in `webhook_attempts` (code, error, duration, 500-char response snippet) = the delivery log.
- **Manual replay**: `POST /v1/webhook-deliveries/:id/replay` (or by event). Same event id is re-sent, a new retry cycle starts (`cycle_attempts` reset), attempt numbering continues, `replay_count` increments; allowed from any state (replaying a succeeded delivery is intentional; receivers dedupe on event id).
- **Worker concurrency/crash safety**: claim with `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING` that pushes `next_attempt_at` forward by a lease (60s). Several workers never claim the same delivery; if a worker dies mid-attempt the row becomes due again when the lease expires. Delivery to merchants is therefore AT-LEAST-ONCE (a crash after the merchant returned 2xx but before we record it re-sends); the stable event id header is what lets receivers make it effectively-once. Ordering between events is NOT guaranteed (retries reorder): receivers should use `createdAt`/fetch current state.
- **SSRF guard**: only http(s), no credentials in URLs, and unless `ALLOW_PRIVATE_WEBHOOK_URLS` (dev only; the service refuses to boot with it enabled in production) hosts that are or resolve to private/loopback/link-local/metadata/CGNAT/multicast addresses are rejected, at creation AND again before every attempt. Known limit: DNS rebinding between check and connect; production should also egress-filter at the network layer.
- **Auth**: merchants use the SAME API key as the payments API. Keys are only hashed inside payments, so webhook-service verifies by calling payments `GET /v1/me` (30s positive cache). Other merchants' ids return 404, never 403. Operator view: `GET /admin/webhook-deliveries`, `/admin/webhook-stats` (admin token).
- **Demo receiver** (`services/demo-receiver`, :3007): a merchant endpoint done right (raw body -> verify signature+timestamp -> dedupe on event id -> act -> 2xx) with fault knobs (`POST /admin/behavior {failNext, failStatus, delayMs}`, `POST /admin/secrets`, `GET /received`).

### Phase 6 decisions (reconciliation-service)
- **Data access**: reconciliation never reads other services' tables. Each source offers a read-only internal feed: ledger `GET /internal/invariants` and `GET /internal/transactions` (type/time window, keyset-paged); payments `GET /internal/reconciliation/payments` (admin token; payments + refunds + their ledger links); the mock bank's `GET /settlement?date=`.
- **Two run kinds**. `internal` = the ledger's own SQL self-audit (sum of ALL balances exactly 0, every transaction balanced, balance == credits-debits recomputed from the journal, held == active holds, no illegal negatives) PLUS payments<->ledger (every settled payment has exactly its ledger movement: customer debited the amount, merchant credited amount-fee, total credits == amount; failed payments have none; no orphan ledger captures; succeeded refunds credit the customer; stuck payments flagged). `external` = payments vs the bank's settlement file (`missing_in_gateway`, `amount_mismatch`, `bank_charge_without_payment` for both failed payments and unknown references). Comparison logic is pure functions over plain data (`src/checks/*`), property-tested.
- **Stored reports**: `recon_runs` (window, status clean/mismatches/failed, summary counts, error) and `recon_mismatches` (kind, severity, reference, message, expected, actual). Findings are critical/warning/info.
- **Never lie about what was checked**: a data source that is down makes the run `failed` with the reason (never "clean", never invented mismatches). The summary always shows how many payments / ledger transactions / bank charges were actually examined.
- **Transient states are filtered**: records newer than `graceMs` (60s) are left out, and findings must appear in TWO passes `confirmDelayMs` (3s) apart. A payment mid-flight (bank charged first, we have not captured yet) therefore does not raise a false alarm. Payments still created/processing are skipped by the external check; the internal check flags the ones that stay stuck beyond `stuckAfter` (default 5 min) as a `warning`.
- **Window padding**: inputs are fetched +/-1 day beyond the window for lookups so a charge/payment on a day boundary still finds its counterpart; only records whose own timestamp is inside the window are reported.
- **One run per kind at a time across replicas**: a Postgres session advisory lock held for the duration; a second caller gets "already running" (HTTP 409 for manual runs, silently skipped for the scheduler). Scheduler (internal 5 min, external 15 min by default; compose uses 60s/120s for demos) runs in every replica; the lock picks the worker.
- **Operator API** (admin token; dashboard login comes later): `POST /v1/recon/runs {kind, from?, to?}`, `GET /v1/recon/runs`, `GET /v1/recon/runs/:id` (with findings), `GET /v1/recon/latest`. Metrics: `recon_runs_total{kind,status}`, `recon_open_mismatches{kind,severity}`, `recon_last_run_timestamp_seconds`.
- **Keyset paging must carry the exact timestamp**: Postgres timestamps have microseconds, a JS `Date` has milliseconds. A cursor built from a Date re-returns the row it came from and can loop forever. Cursors now carry the timestamp as text and compare with a row-value `(created_at, id) > (ts, id)`. Regression test pages one row at a time over concurrently created rows; reverting to Date cursors made it fail with "feed did not terminate".
- **Gotcha: bigserial ids**: `@zerodrift/db` parses BIGINT as JS `bigint` (money safety), so a `bigserial` primary key returned in JSON throws "Do not know how to serialize a BigInt" (HTTP 500). Convert to string at the API boundary. Found because the only tests that returned findings hit it; fixed in recon, audited other services (no other bigserial is returned to clients).

### Phase 7 decisions (dashboard, shop, chaos)
- **A BFF instead of letting the browser talk to services**: `dashboard-api` (:3008) is the only thing the console talks to. It authenticates the operator (JWT), then calls the internal services with their admin tokens. The browser never holds a service credential, services keep a tiny attack surface, and the allowlists below live in one place. It also serves the built React app (same origin: no CORS needed in production).
- **Operator auth**: `POST /auth/login` -> HS256 JWT (1h) via `jose`. Verification pins `algorithms: ['HS256']`, issuer, audience and role, so `alg: none`, forged, wrong-audience and expired tokens are rejected (all with the same message, nothing leaked). Credentials are compared in constant time (hash both, `timingSafeEqual`); both username and password are always evaluated. Login is rate limited (5 failures / 60s per client, then 429 + Retry-After; in-memory per instance). Production refuses to start with the dev JWT secret, dev password or dev admin token. The token lives in `sessionStorage` (gone when the tab closes); the server sends a strict CSP (`default-src 'self'`) so injected script cannot read it. Known trade-off: a cookie with HttpOnly would resist XSS better but needs CSRF protection; revisit in Phase 8.
- **Only allow-listed things are proxied**: query params are whitelisted per route (unknown ones are dropped), ids are UUID-validated before any upstream call, the operator's JWT is never forwarded, and Prometheus is queried only through a FIXED set of named queries (the dashboard is not an open PromQL proxy). A service being down becomes a 502 naming it; the overview and metrics pages degrade instead of failing.
- **Operator read APIs added**: payments `GET /admin/payments`, `/admin/payments/:id`, `/admin/stats`; webhook `GET/POST /admin/webhook-deliveries/:id[/replay]`, `/admin/webhook-endpoints`; ledger transaction feed gained `order=desc`. Payment events now carry the merchant's optional `reference` (backward-compatible field): the demo shop's lost-response test showed a webhook could not otherwise be matched to an order when the create-payment response never arrived.
- **Chaos controller** (dev only). Acts on the REAL containers through the Docker Engine API over `/var/run/docker.sock` (mounted only in compose, effectively root on the host: dev only), on the mock bank's fault knobs, and on Toxiproxy. Whitelist of targets (never databases, the controller or the dashboard). Safety: it refuses to boot with `CHAOS_ENABLED=true` and `NODE_ENV=production`; when disabled every `/chaos/*` route is a 404 even with a valid token; admin token otherwise. **Payments reaches the ledger and the bank THROUGH Toxiproxy** (`:13001`/`:13005`) so "add latency", "black-hole traffic" and "cut link" are real network faults. **Kill + auto-restart**: a plain `docker kill` leaves the container dead (the compose restart policy did not revive it), and a single Docker host has no orchestrator, so `kill` takes `restartAfterSeconds` to emulate one (the panel defaults to 8s; Kubernetes in Phase 9 does the real thing).
- **Load generator in the panel**: fires N payments through a throw-away merchant with ~10% deliberate duplicate requests (same Idempotency-Key) and reports distinct payments vs requested, so idempotency is visible while faults run.
- **Demo shop** (`demo-shop` :3009 + React storefront): the merchant API key stays on the server; prices come from the server catalogue (the browser sends only product ids and quantities); the payment carries `Idempotency-Key: order-<id>` and a repeated checkout attempt returns the SAME order; an unknown outcome (timeout / 202) leaves the order PENDING (never failed) and the signed, deduplicated webhook settles it, matched by `reference`. The storefront reuses ONE checkout Idempotency-Key per attempt, so pressing Pay again after an error cannot double-charge. It provisions its own merchant + webhook endpoint at boot (a new merchant per boot: the API key is only ever shown once).
- **Frontend structure**: `@zerodrift/brand` = the ONE place the product name lives in the frontend; `@zerodrift/ui` = theme tokens (CSS variables, light + dark) + reusable components, so the Phase 11 redesign edits one package. Vite 8 + React 19 + Tailwind 4 (tokens exposed as utilities). Money is formatted from integer paise with `bigint` (exact beyond 2^53). Polling (`useApi`) cancels in-flight requests, keeps the last good data on a failed refresh, and stops on unmount. The console also stays usable when the chaos controller is off (it explains why and shows no destructive buttons).
- **Browser tests run in a container** (`e2e/Dockerfile`, `e2e/run.sh`): the host lacks Chromium's system libraries and has no sudo, so Playwright + Chromium + dependencies are baked into an image attached to the compose network. This is also what Phase 10's screenshots will use.

### Bugs found by running the real UI in a real browser (Phase 7) and fixed
- **One dead dependency starved every other outbound call.** With Prometheus stopped, the Metrics page's ~11 parallel queries each waited ~4s for Docker DNS to fail (flaky resolver), occupying Node's default 4-thread libuv pool; a lookup for a HEALTHY service made during the burst took 10.4s and failed ("payments is not reachable"). Measured, not guessed. Fixes: `UV_THREADPOOL_SIZE=32` in the runtime image for every service; the dashboard's `Upstream` fails fast for 3s after a connection failure; Prometheus gets a 10s negative cache and a 4s result cache. After the fix the whole console and a shop checkout work with Prometheus stopped. **Chaos implication**: on a single Docker host a killed container's name stops resolving for everyone else, which can cascade the same way; Kubernetes services keep a stable address (Phase 9).
- **"Controller unreachable" was reported as "chaos disabled"** (any failure was swallowed). Only a 404 means disabled; an outage is now a visible 502.
- **`crypto.randomUUID is not a function` in the shop** when opened over plain http on a non-localhost hostname (insecure context): replaced with a `getRandomValues` fallback (`apps/shop/src/ids.ts`, tested).
- **Merchant webhooks could not be matched to orders when the create-payment response was lost** (events had `paymentId` but not the merchant's `reference`): optional `reference` added to payment events.
- Test lessons: a test must set up its own state (the chaos "reset" test silently depended on an earlier test leaving Kafka paused); the browser test needs the one deliberate 401 whitelisted.

### Phase 8 decisions (observability, rate limiting, security)
- **Request context** (`@zerodrift/common`): AsyncLocalStorage carries a per-request correlation id (validated, otherwise minted) through every await; HTTP clients forward it (`x-correlation-id`), `emitEvent` stamps it into the event envelope, consumers restore it, so one id finds the logs of one business operation across services and Kafka. Request middleware writes ONE structured log line per request (route PATTERN, status, duration, correlationId, traceId; never query/headers/body), records `http_request_duration_seconds` (histogram) and `http_requests_total`. Quiet for /health /ready /metrics.
- **Tracing** (`@zerodrift/telemetry`, OpenTelemetry, off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set; Jaeger all-in-one in compose :16686). Auto-instrumentation for HTTP/Express/pg/undici(fetch). **Kafka has no automatic carrier**, so the W3C `traceparent` travels INSIDE the event envelope (optional, regex-validated field) and the consumer starts its span with that parent: the async tail of a payment (webhook-service consumer, webhook delivery) is part of the same trace as the HTTP request that caused it. Verified live: one trace spans dashboard-api -> payments -> ledger + mock-gateway -> webhook consumers.
- **Consumer lag** metric `kafka_consumer_lag{group,topic}` (`LagReader`: ONE long-lived admin client per monitor). **Native-crash pitfall**: closing the lag admin client, the consumer and the DLQ producer concurrently (and creating/destroying admin clients per tick) segfaulted librdkafka (SIGSEGV). Fix: one admin client, first read after one interval, `stop()` awaits any in-flight read and tears clients down strictly one at a time; regression test cycles start/stop with a 50 ms monitor.
- **Grafana dashboards as code**: `scripts/gen-dashboards.mjs` generates `infra/grafana/dashboards/zerodrift.json` (27 panels: health stats, throughput, error ratio, p50/p95/p99 latency, consumer lag, outbox backlog, gateway circuit/calls, recovery, webhooks, rate limiter, reconciliation, node runtime); datasources (Prometheus uid `prometheus`, Jaeger) and the dashboard are provisioned; `scripts/verify-dashboards.mjs` runs every panel query against live Prometheus (29 queries, 0 PromQL errors, 25 returning data after traffic; the other 4 are legitimately zero). One Prometheus job per service so series carry `job`.
- **Rate limiting** (payments, Redis, ioredis): per-merchant TOKEN BUCKET (capacity = `rate_limit_per_min`, refill = limit/60 per second) in an atomic Lua script (refill+check+spend cannot interleave; uses Redis TIME so replicas with skewed clocks share one bucket). `X-RateLimit-Limit/Remaining`, 429 + `Retry-After`. **Fails open** (tiny command timeout, no offline queue) so a Redis outage never becomes a payments outage; counted in `rate_limit_decisions_total{result="error_allowed"}`. Bad-API-key throttle per client address (the attempt that crosses the budget is itself refused). Tests on a real Redis: exact quota under 50-way concurrency, shared across two payments replicas, isolation between merchants, refill, fail-open, disabled mode.
- **Audit log** (payments + webhook): `audit_logs`, append-only via trigger (UPDATE/DELETE/TRUNCATE rejected), written in the SAME transaction as the action (payment/refund creation, endpoint changes, secret rotation, replays) or immediately after for admin actions; stores actor, merchant, action, resource, ip, correlation id and small non-sensitive details, never keys/secrets. Operator view `GET /admin/audit-logs`, merged in the console's Audit page.
- **Hardening**: security headers + `no-store` + server timeouts in the shared `bootstrap`; production refuses dev secrets (`refuseDevSecrets`, verified on the real binaries); all services run as `node`; `UV_THREADPOOL_SIZE=32`; `scripts/audit.mjs` (`pnpm audit:deps`, in CI) because `pnpm audit` hung. Full review, accepted risks and findings table: `docs/SECURITY.md`.
